SVP RC2 Agent Orchestration Plan

A staged, branch-based plan for taking SVP from the RC2 spec foundation to a real 30-second video package with first-class OCR and structured color observations, while keeping builders, reviewers, and the orchestrator in a tight wake-up loop.

North Star

SVP is a strict package format for machine-readable observations over time-based media. The goal of this project is to build enough real infrastructure to process one simple 20 to 30 second video into an inspectable RC2 `.svp` package.

Observation layers are core. Interpretive labels are non-core unless explicitly required by the RC2 spec. Visible text, numeric values extracted from visible text, and measured color coverage are Core observations.

Core rule: build the validator and package foundation first. The builder may produce partial packages along the way, but it cannot claim success until the validator can inspect and report on the output.

Validator-first sequencing prevents the project from producing impressive-looking packages that cannot be independently inspected, trusted, or debugged.

The roadmap already contains the phase details. This file explains how the orchestrator should dispatch agents, review PRs, sequence dependencies, and keep the project moving without letting parallel work collide.

What We Are Not Doing

  • No full video builder before the validator spine exists.
  • No more than two builder agents active at once.
  • No builder reviews or merges its own work.
  • No direct edits in another agent's active worktree.
  • No vague "works for me" package validity claims.
  • No god files or catch-all dumping grounds.
  • No tests just for ceremony when no code or behavior changed.
  • No NLE plugin, editor integration, GUI application, or external tool integration during this RC2 infrastructure pass.
  • No Phase 03+, fixture lab, media ingest, vision, index/package, or first-trial dispatch until OCR/color unblock criteria are represented.

What Success Looks Like

  • svp-validator emits structured reports and meaningful validation codes.
  • Fixtures prove valid and invalid package behavior.
  • svp-reader and svp-inspector make packages understandable.
  • The builder creates partial packages first, then a complete package later.
  • One simple 20 to 30 second video produces a `.svp` file, validation JSON, inspector output, and a trial report.
  • Visible text and numeric values are stored as Core observations.
  • Scene, shot, frame, region/entity, and text-region color distributions are numeric and searchable, including queries like "find all orange scenes."
  • Each file has one clear job, and shared contracts have one source of truth.

Minimum Valid RC2 Package For First Video Trial

For the first 20 to 30 second video trial, a package may be considered milestone-valid only if it passes the validator according to the RC2 rules and contains the minimum required package structure defined by the spec.

The first milestone package must include, at minimum:

  • Original media reference or embedded source media according to the RC2 package rules.
  • Required manifest files.
  • Required package metadata.
  • Required provenance records for generated outputs.
  • Canonical timing representation.
  • At least one valid media timeline.
  • Transcript structures when audio is present, or explicit valid zero-word behavior when the source is silent.
  • Required /text/ section with text observations or honest text absence.
  • Required /colors/ section with numeric color observations and summaries.
  • Shot or scene structure if required by the RC2 package rules.
  • Validation report output generated by svp-validator.
  • Inspector-readable package summary.
Spec fidelity rule: if any listed requirement conflicts with the RC2 spec, the spec wins. Agents must adjust implementation and validation behavior to the spec rather than inventing new package requirements.

Optional layers such as labels or model-generated observations may be absent, sparse, empty, or marked unsupported only when the RC2 spec allows that state. Text and color are not labels in RC2; they are Core observations.

No builder may claim a complete package unless the validator confirms it. Partial builder output must be marked honestly as incomplete.

No Silent Spec Decisions

Agents must not silently resolve ambiguous RC2 behavior by inventing implementation behavior. If the spec is unclear, contradictory, or underspecified, the agent must document the ambiguity and escalate to the orchestrator or human owner.

Implementation may use temporary behavior only when:

  • It is clearly marked as temporary.
  • It uses documented temporary validation codes where relevant.
  • It does not change RC2 semantics.
  • It includes a follow-up recommendation.

Branch And Worktree Model

All agent work happens on scoped branches with fresh worktrees. The orchestrator decides the branch base for each assignment after checking current repo state.

main or current integration branch | +-- codex/phase-00-repo-baseline +-- codex/phase-01-build-system-cli +-- codex/phase-02-validator-core +-- codex/phase-08-model-runtime +-- codex/phase-06-media-ingest +-- codex/phase-04-fixture-lab
Important: every builder gets a new worktree and a scoped branch. Builders may commit, push, and open PRs for their assigned scope. Reviewers may review and approve or request changes. The orchestrator coordinates merge readiness and the next assignment.

Shared Source Of Truth Rules

The following concepts must have one source of truth:

  • Validation code registry.
  • Validation report schema.
  • Package manifest field names.
  • Canonical timing and rational time conversion.
  • Hash algorithms and hash formatting.
  • SVPB block type identifiers.
  • Model bundle identifiers.
  • SQLite index schema.
  • Exit code behavior.
Review rule: builders must import or reuse shared definitions instead of copying strings, constants, or schema fragments into tool-specific files. Duplicate constants should be treated as review findings unless the duplication is explicitly generated from the canonical source.

Agent Loop

This is the operating loop for the whole project. It is intentionally repetitive, because repetition keeps a large multi-agent project boring in the best way. Wake-up loop means each builder or reviewer explicitly reports completion back to the orchestrator, including status and next recommended task.

Default approval rule: a builder PR may be considered ready after a separate reviewer thread approves it and the orchestrator confirms scope, proof, and dependency safety. Human escalation is reserved for product intent, ambiguous spec judgment, credentials, local environment decisions, and destructive git permission.
File responsibility guardrail: line count is a signal, not the real rule. Files should be easy to reason through and have one clear responsibility. Split code into packages, tools, formatters, parsers, report models, readers, writers, and policies according to ownership. Do not create new god files while building the foundation.

Orchestrator Selects The Next Phase

The orchestrator checks dependency gates, open PRs, blocked shared files, and the two-builder limit. It assigns only the next safe phase or review.

Builder Thread Creates Branch And Worktree

The builder reads AGENTS.md, the common roadmap docs, and only the assigned phase doc. It creates a fresh worktree, implements the scoped work, verifies appropriately, commits, pushes, opens a PR, and wakes the orchestrator.

Reviewer Thread Reviews The PR

The reviewer checks behavior, source-of-truth ownership, shared contract safety, file responsibility, and proof. Reviewers run commands only when needed to prove or disprove something.

Builder Handles Required Changes

If the reviewer requests changes, the builder stays on the same branch and fixes only the requested issues. The builder wakes the orchestrator again when ready.

Orchestrator Advances The Dependency Graph

After approval and merge readiness, the orchestrator marks the phase complete, unblocks dependent work, and starts the next builder or reviewer thread.

Wake-up rule: every builder and reviewer must wake the orchestrator thread when finished. The final handoff must include Next recommended task so the loop can continue without guessing.

Builder PR Definition Of Done

A builder PR is not ready for review until it includes:

  • Scoped implementation matching the assigned phase.
  • No unrelated cleanup or later-phase implementation.
  • Clear file ownership with no new god files.
  • Updated docs only when behavior or usage changed.
  • Relevant verification output, or a clear reason verification could not run.
  • Honest status of partial or incomplete outputs.
  • A final handoff comment containing summary of changes, files changed, verification performed, known limitations, and next recommended task.

Reviewer Definition Of Done

A reviewer thread must finish with one of these statuses:

  • Approved.
  • Changes requested.
  • Blocked pending human or orchestrator decision.

Reviewer output must include:

  • Findings first, ordered by severity.
  • Whether the PR stayed inside scope.
  • Whether changed behavior had adequate proof.
  • Whether shared contracts were modified safely.
  • Whether any god-file or mixed-responsibility risk was introduced.
  • Exact required changes if not approved.
  • Next recommended task for the orchestrator.

Risk Register

Risk Why It Matters Mitigation
FFmpeg and probing drift Media duration, frame rate, timebase, and audio stream behavior can vary by file and platform. Require deterministic probe output, canonical rational timestamp conversion, and timestamp tests for common frame rates.
Timestamp correctness Small timing errors can poison transcript alignment, shots, scenes, tracks, indexes, and validator results. Treat rational time conversion as shared core logic with focused tests. Do not duplicate timestamp math across packages.
Validator scope creep Phase 3 can become too large if schema, SVPB, hashes, SQLite, and logical row checks are all implemented as one blob. Split validator deep checks internally into focused owners and review checkpoints.
Model runtime instability ONNX Runtime, model bundles, cache discovery, and missing model behavior can block builder progress. Keep model runtime isolated in packages/svp-models; missing models must produce clear non-crashing errors.
SVPB parsing complexity Binary stream parsing can become fragile and hard to debug. Give SVPB parsing its own focused module, tests, and validation codes.
SQLite/index correctness A package can look structurally valid while its index is stale, incomplete, or logically inconsistent. Validate index manifest, expected tables, logical row hashes, and package-to-index consistency.
Package size growth Masks, depth, embeddings, and indexes can make packages large quickly. Permit sparse outputs where valid; defer heavy layers until basic package validity is proven.
Agent scope creep Builders may wander into later phases or perform unrelated cleanup. Keep scoped branch assignments strict; reviewers must reject unrelated changes.
Shared contract collisions Multiple agents editing build files, validation codes, or core contracts can create merge conflict sludge. Orchestrator must explicitly coordinate shared contract files and avoid parallel edits in those zones.
Spec ambiguity Agents may silently resolve unclear RC2 behavior in code. Ambiguities must be documented and escalated instead of silently changing RC2 semantics.
OCR/color under-specification Text and color are now Core observations. If agents treat them as labels or optional add-ons, validator, fixtures, builder, index, and trial work will drift immediately. Color query mismatch Scene/shot color search such as "find all orange scenes" requires numeric color coverage in the package and index, not only visual embeddings or text color. Store registry-backed color bucket percentages for scenes, shots, frames/keyframes, regions/entities, and text regions where applicable.

Testing And Verification Discipline

Tests and verification commands should prove the work that changed. They are not a ritual tax.

Verification skip rule: skipping verification is acceptable only when the PR did not change code, scripts, schemas, generated fixtures, CLI behavior, package bytes, validation behavior, or build configuration. If any of those changed, the builder must either run the relevant proof command or report the exact blocker.
Work Type Expected Proof When To Skip
Docs-only plan updates Readback or browser check when layout matters. When no code, script, schema, or behavior changed.
Build system or C++ code Configure/build command from the phase doc, plus relevant CLI smoke command. Do not skip unless blocked by dependency or environment; report the blocker.
Validator behavior JSON output and exit behavior for valid, invalid, and unreadable inputs. Only skip commands a previous PR already proved and this PR did not affect.
Fixtures Fixture generation command and validator status checks. Do not skip if fixture bytes or generator logic changed.
Reviewer pass Code-review findings first. Run commands only if needed to verify a concern. When prior builder proof is relevant and the reviewer has no reason to doubt it.
